# Landing Page Intelligence Stack Design

**Date:** 2026-07-25
**Status:** Approved for implementation
**Repository:** `/home/mike/nebula`
**Application:** `customer-portal`

## Decision

Build a direct-download, evidence-grade workflow bundle with a dedicated learning-centre acquisition page and a secondary CTA into the existing live audit.

## Approaches considered

### 1. Article only

Publish an article describing the six workflows but provide no usable artifact.

- **Advantage:** Smallest implementation.
- **Failure:** Repeats the generic SEO-content pattern and does not demonstrate product quality.

### 2. Direct-download workflow bundle — selected

Publish the article and a versioned ZIP containing six inspectable workflows, a README, an evidence schema, and a manifest. No email is required.

- **Advantage:** Immediate value, inspectable methodology, low privacy cost, and a clean path to the live audit.
- **Trade-off:** Requires deterministic archive generation and drift checks.

### 3. Gated lead magnet

Require an email before delivery and send the archive through an automation.

- **Advantage:** Captures contact data.
- **Failure:** Adds privacy, delivery, suppression, and outbound-governance complexity before the resource has demonstrated demand. It also conflicts with Nebula's current no-signup audit experience.

## Product boundary

The first release is one static acquisition surface and one static downloadable product. It does not introduce a new application, API, database, account system, checkout, newsletter workflow, or outbound campaign.

## Architecture

### Source bundle

Store human-readable source files under a dedicated repository directory. The source contains:

- `README.md`
- `manifest.json`
- `evidence-record.schema.json`
- Six Markdown workflow files

Each workflow defines:

- Purpose
- Required inputs
- Evidence boundaries
- Numbered execution steps
- Output contract
- Fail-closed conditions
- Verification checklist

### Deterministic packager

A Node script validates the source manifest and generates a ZIP in `customer-portal/public/downloads/`.

The packager must:

- Allow only declared relative paths.
- Reject traversal, absolute paths, duplicates, undeclared files, missing files, and symlinks.
- Sort entries deterministically.
- Normalize archive timestamps and permissions.
- Support `--check` mode that compares generated bytes with the committed projection.
- Emit a manifest-level version inside the archive and a deterministic `.sha256` sidecar beside the ZIP for verification. The digest is not presented as a customer outcome.

### Public page

Create `/learning-centre/landing-page-intelligence-stack` using existing App Router and design-system patterns.

Page structure:

1. Direct answer: what the stack is and who it is for.
2. Primary direct-download CTA.
3. Six workflow summaries with artifact outputs.
4. Evidence rules explaining what the workflows will and will not claim.
5. How to use the bundle.
6. Secondary CTA to `/audit`.
7. FAQ covering format, data handling, tooling, and limits.

The page uses one H1, semantic sections, shared buttons/cards, Karla typography, near-black surfaces, and Signal Emerald only for actions or positive verification states.

### Discovery

Add `meta.json` for the existing learning-centre index and sitemap discovery. Add canonical metadata and appropriate Article or CreativeWork JSON-LD without unsupported ratings, usage counts, or performance claims.

## Data flow

1. Maintainer edits source workflow files and manifest.
2. Packager validates sources and creates the deterministic ZIP.
3. CI runs packager `--check` before build.
4. Next.js serves the page and static ZIP from the same domain.
5. Visitor downloads directly with no form submission.
6. Visitor may follow the secondary CTA to the existing `/audit` flow.

No visitor data is created by the download itself beyond existing aggregate web-server and consent-governed analytics behavior.

## Evidence and claim policy

- The bundle may describe Nebula's documented seven-point method only through existing verified registry material.
- The page may describe what each workflow outputs because those files are inspectable.
- The page must not claim measured conversion lift, time savings, customer adoption, tool replacement, or revenue impact without verified evidence.
- External BuildWire text is competitive research data only; none of its claims or skill content is copied into the product.

## Error handling

- Invalid source or manifest: packager exits nonzero and produces no replacement archive.
- Drift: `--check` exits nonzero.
- Missing archive: integrity test and production build fail.
- Invalid public metadata or unsupported claim: existing metadata/evidence tests fail.
- Download failure in production: rendered QA is a release blocker.

## Testing strategy

Use vertical TDD slices:

1. Archive contract test fails before packager/source exists; implement minimum deterministic bundle.
2. Public-surface test fails before route exists; implement page and metadata.
3. CI drift test fails before workflow/package script wiring; add explicit gate.
4. Rendered E2E test verifies the CTA, download response, one H1, and audit navigation.
5. Full typecheck, lint, Jest, Playwright, production build, dependency audit, and independent adversarial review.

## Rollback

Remove the new route, metadata, bundle source, generated ZIP, packager, and its CI/package-script wiring. No data migration or infrastructure rollback is required.

## Compliance assessment

- **Audit-pipeline extension:** Compliant; the feature links to the existing audit but does not change scoring, delivery, lead state, or email behavior.
- **Lead-pipeline extension:** Not applicable; no lead creation, send, stage transition, or canonical-ledger write.
- **Compliance-sovereignty extension:** Compliant; no model inference or personal data is introduced, and no certification claims are added.
- **Security/property-based/resiliency optional extensions:** Disabled in current AI-DLC state. The implementation still includes deterministic and adversarial archive validation as normal product safeguards.

## Acceptance boundary

This design is approved for implementation only after user review. Implementation must remain inside this boundary; any email gate, payment flow, backend endpoint, or outbound distribution requires a separate approved unit.
