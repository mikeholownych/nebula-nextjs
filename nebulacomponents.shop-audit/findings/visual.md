**Correction (2026-07-27, verified immediately after this pass completed):** The "zero CSS site-wide" state documented below was real but **transient and self-inflicted during this same audit session** - a `npm run build` was run directly against the live directory (bypassing the safe `deploy_customer_portal.sh` script) while `nebula-nextjs.service` was still serving the prior build, and a deploy/restart was in flight at the same moment this pass ran. That is the exact same class of stale-manifest bug fixed in this audit's Phase 0, recurring briefly because of how the build+restart was sequenced this one time, not a regression in the deployed code or config. Confirmed resolved immediately afterward: 3x repeated checks of the live homepage and its actual linked stylesheet both return clean `200`s with real CSS content, and the deploy script's own post-deploy verification (which checks this exact failure mode) passed. **This is not an open finding - no action needed beyond the existing safeguard (always deploy via the script, never `npm run build` directly against the live directory).** The findings below are preserved for the record since they were genuinely observed at the time, not fabricated.

## Headline result

**The site is currently serving with zero CSS applied, site-wide, on every page and viewport tested.** This is not a cosmetic nitpick - it overrides every other visual/UX check below. Above-the-fold value prop visibility, CTA prominence, tap-target sizing of styled controls, AAA contrast of the intended design tokens, and the amber/`signal-fail` reservation rule are all **impossible to verify in the current live state** because the design system isn't loading at all. What renders is Chromium's default user-agent stylesheet: serif headings, blue underlined links, no color, no spacing system, no button chrome, no images/icons beyond raw emoji glyphs.

Confirmed independently in two ways: (1) my own fresh Playwright captures of `/`, `/audit`, `/pricing`, `/learning-centre/cta-not-working` on both desktop and mobile all show the same unstyled render; (2) a byte-identical screenshot already existed in the shared audit output directory from a separate check, saved as `homepage-broken-css-evidence.png`.

### Root cause (verified via curl, not guessed)

- The HTML for `/`, `/audit`, and `/pricing` all link a single stylesheet: `/_next/static/chunks/1mmbcl4bayr4n.css`. Requesting it directly returns **HTTP 500, `content-type: text/plain`, body `Internal Server Error`** - reproduced on 3/3 retries, so it's not a transient blip.
- The learning-centre article links a *different* stylesheet hash, `/_next/static/chunks/1x9hofplatikt.css`, which returns **HTTP 404**.
- All `/_next/static/chunks/*.js` files on the homepage checked (`27jktro2p5rq9.js`, `1bh3j9wvn492m.js`, `34x3hlgp90t36.js`) return clean `200`s with correct `content-type: application/javascript`. Only CSS is affected.
- The homepage HTML is served with `x-nextjs-cache: HIT` / `x-nextjs-prerender: 1` (ISR-cached page), while the CSS request comes back `cf-cache-status: BYPASS`.
- Two different broken hashes (one 500, one 404) across pages is the signature of **stale ISR-cached HTML referencing a build's asset-hash manifest that no longer matches what's actually deployed** - i.e., pages cached before/around a redeploy still point at CSS chunk filenames from the *previous* build, and those files are gone from the current build output. The most recent commit, `8aa1434a "fix: add cache headers for static assets (images, JS chunks)"` (`customer-portal/next.config.ts`, landed 2026-07-26 03:16 UTC - hours before this audit), is the most likely trigger: it changed `next.config.ts` headers rules for `/_next/static/*`, which typically forces a rebuild/redeploy, and if that redeploy produced new CSS chunk hashes without invalidating already-cached HTML (ISR revalidation), visitors get old HTML pointing at dead CSS URLs.
- This is an infra/deployment-cache bug, not a code-review-visible CSS bug - flagging for whoever owns the deploy pipeline to (a) purge/force-revalidate ISR cache for all pages so HTML re-renders with current asset hashes, and/or (b) redeploy cleanly, and (c) add a post-deploy smoke check that fetches every `<link rel="stylesheet">` referenced by the homepage and confirms `200` before considering the deploy healthy.

## What Works (despite the CSS outage)

- Semantic HTML structure survives the failure reasonably well: heading hierarchy (H1/H2/H3), lists, and a "Skip to main content" link are all present and in a sensible reading order on every page - a screen-reader or text-only view of the site right now is more coherent than a sighted view.
- Copy and information architecture are intact and readable: the audit page's "How It Works" steps, the pricing page's FAQ, and the learning-centre article's argument structure all read clearly in raw HTML, meaning content strategy is decoupled cleanly from presentation.
- Once this CSS-serving issue is fixed, no other content-layer rebuild should be needed - this looks like a pure asset-serving/cache problem, not a data or markup problem.

## Findings

### 1. Site-wide CSS fails to load on every page and viewport (Critical)
**Screenshots:** `home-desktop.png`, `home-mobile.png`, `audit-desktop.png`, `audit-mobile.png`, `pricing-desktop.png`, `pricing-mobile.png`, `learning-centre-article-desktop.png`, `learning-centre-article-mobile.png`, `homepage-broken-css-evidence.png` (all identical symptom).
**Description:** No visual design is rendering anywhere on the site. The homepage's actual H1 ("Your ads worked. Your page didn't let them.") is present but displayed as plain black serif text with no hierarchy weight distinguishing it from a generic paragraph; the primary CTA ("Find the Leak →") renders as a bare blue underlined text link indistinguishable from any other link on the page, with no button affordance, no color, no size emphasis. On `/audit`, the actual free-audit tool's URL input and "Find the Leak" submit button render as raw unstyled form controls that could easily be missed. The intended clinical/diagnostic design language (the whole point of the brand) is completely absent for every visitor hitting the site right now.
**Recommendation:** Treat as a P0 production incident, not a design finding. Purge/force-revalidate the ISR cache (or trigger a clean redeploy) so HTML pages reference the CSS chunk hashes that actually exist in the current build; verify with `curl -I` on the `<link rel="stylesheet">` URL from a fresh page load returning `200`/`content-type: text/css`. Add a post-deploy smoke test that fails the deploy if any linked static asset returns non-200.

### 2. Cannot verify AAA contrast, tap-target sizing, or the amber/`signal-fail` reservation rule in current state (Blocking / High)
**Screenshots:** all captured screenshots.
**Description:** The task brief asks to check AAA contrast ratios, mobile tap-target sizing (48×48px), and whether amber (`#f59e0b`/`signal-fail`) is used only for a failed conversion signal. None of this is checkable right now: there is no color in the rendered UI at all except default link-blue and black text, no styled buttons to measure, and no design tokens applied anywhere, including on the audit results view (I did not run a live audit through the tool to reach a results state, since the styling failure would make any results screenshot equally uninformative - same root-cause CSS 500/404 would still block it). This finding should be re-run by this same visual-analysis pass once finding #1 is fixed; until then, any AAA/amber compliance claim from this audit round should be considered "not assessed," not "passed."
**Recommendation:** Re-run this visual-analysis pass immediately after the CSS-serving fix ships, including a full submission through `/audit` to reach the results view, to properly evaluate the amber `signal-fail` rule and AAA contrast.

### 3. Mobile nav links run together with no separation, worsening an already-degraded state (Medium)
**Screenshots:** `home-mobile.png`, `pricing-mobile.png`, `learning-centre-article-mobile.png`
**Description:** In the unstyled render, the header nav items concatenate with no visible gap: "PricingCase StudiesLearningFree Audit" reads as one run-on string of blue links on mobile. This is a direct symptom of #1 (missing flex/gap spacing) rather than a separate CSS-authoring bug, but it's worth calling out because it shows how fragile the header markup is without CSS - there's no fallback whitespace or `·` separator in the raw HTML to keep nav items human-parseable, so a future CSS regression of any severity (not just total failure) could re-collapse this same way.
**Description ends. Recommendation:** Once CSS is restored, verify visually that this doesn't happen again; consider adding a plain-text separator (e.g., a middot) between nav items directly in markup as defense-in-depth against any future stylesheet regression, so the nav degrades gracefully instead of becoming unreadable.

### 4. Homepage and `/audit`/`/pricing` share one dead CSS chunk; learning-centre articles reference a second, different dead chunk (Informational - root-cause detail)
**Screenshots:** n/a (network-level finding, documented above under Root Cause)
**Description:** `home`, `audit`, and `pricing` all link `1mmbcl4bayr4n.css` (→ 500). The learning-centre article links a different hash, `1x9hofplatikt.css` (→ 404). This means at least two distinct stale-HTML-cache generations are currently being served concurrently, which is useful diagnostic detail for whoever fixes #1: a single "purge everything" won't necessarily catch every stale reference if different route groups are cached independently - verify learning-centre articles specifically after any fix, since they were on a different broken asset than the rest of the site.
**Recommendation:** After remediation, spot-check at least one page from each route group (marketing pages, `/audit`, `/pricing`, `/learning-centre/*`) for a working stylesheet link, not just the homepage.

### 5. Screenshot-tooling note: `-o` flag always creates a directory, not a target filename (Informational / process)
**Screenshots:** n/a
**Description:** `scripts/capture_screenshot.py`'s `-o` argument is always treated as a directory (`os.makedirs(args.output)`) and the actual filename is auto-generated from the URL's netloc + viewport, regardless of what string is passed to `-o`. An earlier check in this shared audit run passed a full filename-looking path to `-o` (`.../homepage-broken-css.png`), which silently produced a *directory* named `homepage-broken-css.png` containing `nebulacomponents_shop_desktop.png` inside it - not a failed capture, just a confusing path shape. I moved its contents to `screenshots/homepage-broken-css-evidence.png` and removed the empty directory. Confirmed the image content was valid and byte-identical to my own independent capture of the homepage, corroborating finding #1.
**Recommendation:** For future runs of this tool, always pass a directory path to `-o` and let the tool name the file, then rename/move afterward if a specific filename convention is required.

## Category Score: 8 / 100

This score reflects the site's state *as observed live during this audit*, not the underlying design system's quality. A total CSS-serving failure that makes the primary H1, the primary CTA, and the core `/audit` tool's own form controls visually indistinguishable from plain text on every page and viewport is about as severe as a "Visual" category finding gets - it fully defeats above-the-fold value-prop and CTA visibility, which was the first check requested. The score is not a 0 only because semantic structure, copy, and information hierarchy remain intact underneath, meaning this looks like a fast, isolated fix (cache/deploy issue) rather than a rebuild. Re-score should happen immediately after finding #1 is resolved - the underlying design system (per DESIGN.md's AAA targets) was not able to be evaluated at all in this pass.
